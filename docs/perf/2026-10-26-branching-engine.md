## 측정 방법

- 시간은 Mac의 테스트가 잰다. API 호출은 `kubectl port-forward`로 API 서버 Service에 보내고(계획 5 결정 3), 응답 시간은 요청을 보내 본문을 다 받을 때까지다. port-forward의 왕복이 매번 더해진다.
- 브랜치 생성: `POST .../branches`가 201(데이터 준비 끝, 5초 안)을 줄 때까지. 202는 5초 안에 데이터가 준비되지 않은 것이다. 같은 부모의 백업 모드 복사 사이 최소 간격(`minCopyInterval`, 스펙 7.2) 5s에 0.5초를 더해 기다린 뒤 만든다. 간격 제한에 걸린 시간을 재지 않으려는 것이다. 롤백 전의 복구 지점(`rb`의 복사)도 같은 간격을 둔다.
- 첫 쿼리: 201을 받은 때부터 새 port-forward → 접속 → `SELECT 1`이 성공할 때까지, 100ms마다 다시 시도한다. port-forward 준비 시간이 들어 있고, 보조 수치에 따로 적는다. 실제 클라이언트는 클러스터 안에서 Service로 바로 붙으므로 이 몫이 없다.
- 롤백: `rb`(main의 복사본, pgbench 데이터 1.03 GiB (1105442483 bytes))에 복구 지점을 만들고 곧바로 `POST .../rollback`이 200을 줄 때까지. 매번 롤백이 만든 백업 브랜치(정지 상태지만 파드가 노드 자리를 차지한다)와 복구 지점을 지우고, 백업 브랜치가 사라질 때까지 기다린다.
- 정지 → 실행: `rb`를 `POST .../stop`(200, Stopped) 뒤 `POST .../start`가 200(Running)을 줄 때까지. 정지 시간도 보조로 적는다.
- 롤백 요청 → rb Running(보조): 롤백 요청을 보낸 때부터 API가 `rb`를 Running으로 보일 때까지, 250ms마다 조회.
- 쓰기 부하 조건의 롤백과 정지 → 실행은 main의 부하에 더해 `rb` 자신에도 `pgbench -c 4 -N`을 같은 방법으로 돌린다. 표본마다 부하를 시작해 `pg_stat_activity`에 활성 세션이 보인 뒤 5s 더 쓰고서 잰다(복구 지점도 그동안 만든다). 롤백과 정지가 `rb`의 PostgreSQL을 내리므로 부하는 표본마다 끝나고 다음 표본에서 다시 시작한다. 정지는 부하가 더럽힌 버퍼의 종료 체크포인트를 치른다.
- 프로젝트 생성: `POST /v1/projects`부터 phase Ready까지(init-main 포함), 200ms마다 조회. 매번 지우고 네임스페이스가 사라질 때까지 기다린다.
- 측정한 브랜치는 다음 측정 전에 지우고 사라질 때까지 기다린다. 노드(아래)에 브랜치 파드(500m·1Gi)가 20개 들어가지 않기 때문이다. 두 조건은 차례로 돈다.
- 백분위는 최근접 순위다(20회면 P50은 10번째, P95는 19번째).
- 쓰기 부하: main에 `pgbench -i -s 70`(16s 걸림, 데이터베이스 1.03 GiB (1105442483 bytes)) 뒤, 쓰기 부하 조건 내내 main에서 `pgbench -c 4 -N`. pgbench는 **main 파드의 postgres 컨테이너 안에서 `kubectl exec`로** 파드의 Unix 소켓에 붙어 돈다. 프로젝트의 `branch-ingress` 정책은 5432를 `consonance-system`과 볼륨 에이전트 라벨(`app.kubernetes.io/component`)의 파드에만 연다. 그 라벨을 단 파드는 에이전트 Service의 엔드포인트가 되어 에이전트로 가는 요청을 받게 되므로 쓸 수 없고, 측정 때문에 제품의 네트워크 정책을 넓히지 않는다. 그래서 부하를 만드는 클라이언트가 부하를 받는 브랜치의 CPU 한도(브랜치 파드 요청 CPU 500m·메모리 1Gi, 한도 CPU 500m·메모리 1Gi)를 PostgreSQL과 나눠 쓴다. 비밀번호는 E2E처럼 API(`GET .../connection`)에서 받아 exec의 표준 입력으로 넘기고 어디에도 찍지 않는다. 클라이언트가 중단(`aborted`)되거나 0 tps인 5초 구간이 있으면 테스트가 실패한다.

## 쓰기 부하에서 브랜치 생성이 기준을 넘는 까닭

- 이 실행에서: 백업 모드 복사가 main에 거는 즉시 체크포인트(`pg_backup_start(fast := true)`, 스펙 2장 "체크포인트 비용")가 P50 1.50s 걸렸다. 그 체크포인트는 버퍼 P50 9453개를 썼고, 쓰기 단계가 P50 1.34s, sync 단계가 P50 0.03s다. 에이전트의 복사 전체는 P50 2.22s다. 부하 없음에서는 같은 체크포인트가 P50 0.02s다.
- 체크포인트가 쓰는 버퍼는 직전 체크포인트 뒤에 부하가 더럽힌 페이지다. `-N`은 1GB `pgbench_accounts`의 임의 행을 고치므로 복사 사이(약 7초)에 버퍼가 더럽혀진다. 이 실행에서는 P50 9453개이고, 버퍼 하나가 8KB라서 약 74MB다.
- 시간은 쓰기 단계에서 든다. 2026-10-26의 제한된 실험(같은 크기의 프로젝트, main에 같은 부하, 설정마다 브랜치 생성 5회, main cgroup의 PSI와 `cpu.stat`)에서:
  - 기본 설정: 쓰기 0.94~3.45초, sync 0.02~0.10초. 생성 한 번 사이에 main의 `io.pressure` 0.5~1.5초, CPU 스로틀링 0.2~1.8초, `memory.pressure` 10ms 이하.
  - main을 CPU 2로 늘림(스로틀링 0): 쓰기 1.29~2.78초로 그대로, `io.pressure`는 0.6~1.6초로 늘어남. CPU 한도는 주된 원인이 아니다.
  - `checkpoint_flush_after = 0`(쓰기 중 강제 writeback 끔): 쓰기 1.43~2.85초, sync가 0.37~1.10초로 늘어 합은 그대로. memcg의 더러운 페이지가 105~125MB에서 멈췄다 줄어든다. 1Gi 한도의 memcg에서 dirty 한계에 닿아 쓰기가 장치의 writeback 속도로 묶인다.
  - `bgwriter_lru_maxpages = 1000`, `bgwriter_lru_multiplier = 10`, `bgwriter_delay = 10ms`: 쓰기 시간과 생성 P50이 나아지지 않았다(생성 P50 2.44초). 체크포인트가 쓰는 버퍼 수의 변화는 확인하지 못했다.
  - `checkpoint_timeout = 30s`: 버퍼는 반으로 줄지만 체크포인트가 겹쳐 생성 P50 3.96초, 202 두 번. 더 나쁘다.
  - 머신 디스크: 8k `O_DIRECT` 쓰기 99MB/s, 1M `O_DIRECT` 996MB/s, 8k 버퍼 쓰기 + fsync(순차) 733MB/s. 체크포인트의 흩어진 8k 페이지는 작은 쓰기의 속도(동시 WAL fsync와 나눠 약 60~80MB/s)로 나간다.
  - 부하 중 reflink 복제(`FICLONE`)가 0.3~1.5초로 길어졌다(부하 없음 0.1초 안팎). 원본 파일의 더러운 페이지를 복제 전에 먼저 내보내기 때문일 가능성이 높지만, 따로 가려내지는 못했다.
- 결론(추정): 가장 큰 원인으로 보이는 것은 Podman 머신 가상 디스크의 작은 쓰기 속도이고, 호스트 경합이 두 번째 변수다(아래 측정 환경 표의 호스트 상태 행, 스왑 사용량과 머신 PSI). 위 실험은 호스트 경합을 따로 떼어 보지 않았으므로 둘의 몫은 나누지 못했다. 복사마다 강제 체크포인트를 거는 설계(스펙 2장)가 그 비용을 생성 시간에 넣는다. 위의 설정은 어느 것도 P50을 1초 아래로 내리지 못해 채택하지 않았다. 제품 설정은 바꾸지 않았다.
- 같은 조건에서 새 브랜치 첫 쿼리도 기준을 넘었다(P95 3.72s, 기준 3.00s). **검증하지 않은 가설**: 새 브랜치는 복사하는 동안(에이전트의 복사 전체 P50 2.22s) main이 쓴 WAL을 기동할 때 다시 적용하므로 부하가 있으면 첫 접속까지가 길어지고, 여기에 호스트 경합이 더해졌을 것이다. 이 실행에서 가려내지 않았다. 같은 조건의 첫 전체 실행에서는 P95가 1.63초였다.
